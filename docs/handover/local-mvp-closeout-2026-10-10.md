## المانع الرئيسي

التشغيل `run_1791578705104_wql8g` قرأ `README.md`, `package.json`, `src/App.tsx` بنجاح. نتيجة grounding احتوت `MISSING_EVIDENCE_REFERENCE` لعبارات غير مرتبطة بالمراجع، بما فيها عنوان ملاحظة. الحالة النهائية `AWAITING_INPUT` برمز `CONVERSATION_CONTINUES`، وAgentRun بحالة `PAUSED`. التقرير لم يحتوِ الملاحظات والخطة الكاملة المطلوبة.

المسار ذو الصلة: `backend/src/agent-runtime/inspection/agent-inspection.service.ts`، فرع `!reply.action` قرب الأسطر 706 إلى 730، وفروع checkpoint والتقرير قبله. هذا يثبت موضع الانتقال والحالة الناتجة؛ تحديد سبب الرد غير المكتمل يحتاج تتبع الرد والتصنيف والـgrounding قبل اختيار تعديل محدود. لا تُزال متطلبات الدليل لتحويل النتيجة إلى نجاح.

## خطوات القفل بالترتيب

كل بوابة لا تُغلق إلا بدليلها، وأي فشل يبقى ظاهرًا حتى إصلاح سببه. النطاق الحالي حفظ التسليم وترتيب العمل؛ تنفيذ الإصلاحات التالية يكون في مرحلة العمل التالية.

### 1 تشخيص وإصلاح إتمام مهمة Agent

تتبع الرد الأصلي إلى parser، تصنيف العبارات، ربط المراجع، قرار final أو action، ثم الانتقال إلى انتظار المستخدم. ميّز عنوان القسم والمقترح عن الادعاء الواقعي. صحّح مسار توليد المراجع وتصنيف التقرير، واستخدم تصحيحًا محدودًا من الأدلة المحفوظة عندما لا توجد معلومة مطلوبة فعليًا من المستخدم. حافظ على رفض الادعاءات غير الموثقة.

**معيار القبول:** الطلب الحالي ينتج وظيفة التطبيق وطريقة تشغيله، ملاحظات بالعدد الذي تسنده الأدلة مع مسار ومقتطف، وثلاث مراحل لكل منها هدف ومعيار تحقق. ينتقل إلى COMPLETED فقط بعد تحقق النتيجة. الانتظار للمستخدم يعرض سؤالًا محددًا عندما تكون الإجابة ضرورية فعلًا.

**الدليل:** اختبارات للعنوان مقابل الادعاء، مراجع مفقودة أو قديمة، تقرير غير مكتمل دون سؤال، تقرير كامل بمراجع صحيحة؛ ثم تشغيل حي في محادثة جديدة والمحادثة الطويلة مع حفظ التقرير والإيصالات والحالة. لا تعِد القراءات الناجحة تلقائيًا لمجرد توقف التحليل.

### 2 تثبيت حالات الواجهة والتقدم

راجع تسميات Paused وWaiting for clarification، عرض سبب توقف grounding، التمييز بين انتظار الموديل والعملية المحلية، وكيفية استكمال المهمة. حافظ على الشات والمحرر وإجراءات المراجعة قابلة للاستخدام أثناء نشاط القراءة.

**معيار القبول:** يظهر السبب الحقيقي والإجراء المناسب، ولا يوحي التطبيق بضرورة توضيح مهمة واضحة. لا تظهر Completed لتقرير غير مكتمل، ولا يُفقد التقدم عند تبديل اللوحات أو Reload. لوحة المفاتيح والشاشة الصغيرة تدعمان المسار الأساسي.

**الدليل:** سيناريوهات نجاح وتوقف واستكمال، DOM وصور، مقارنة معرفات التشغيل والإيصالات قبل وبعد Reload، وعدم وجود إرسال أو تنفيذ مكرر.

### 3 إثبات تعديل الملف عبر Runtime

أعد فحص الجلسة والـGrant والـenrollment والـbinding وهوية Runtime والبروتوكول والتوقيع الحالي. أعد قراءة الملف للحصول على preimage حديث. راجع الاقتراح المحدد والتعليق أعلاه، ثم احصل على الموافقة المحددة داخل مسار التطبيق ونفّذ الكتابة المشروطة مرة واحدة. إذا تغيّر المصدر فحضّر اقتراحًا جديدًا؛ لا تعِد تنفيذ عملية ذات نتيجة غامضة.

**معيار القبول:** فرق محدود بالتعليق فقط، expected-original SHA256 صحيح، كتابة ناجحة بإيصال موثق، قراءة Runtime مستقلة تطابق المحتوى النهائي، التقرير محفوظ، ثم Reload بلا كتابة مكررة. لو لزم استرجاع التعليق، يكون باقتراح جديد وموافقة مستقلة.

**الدليل:** الاقتراح وبصمته، الموافقة والـpermit، بصمتا قبل وبعد، diff، إيصال الكتابة وread-back والتقرير، مقارنة عدد التنفيذات بعد Reload. موافقة هذه المحادثة على حفظ التسليم لا تجدد grants ولا توافق تلقائيًا على اقتراح الكتابة المعلق.

### 4 تشخيص الأداء وتحسينه

افصل زمن الشبكة والموديل عن انتظار قاعدة البيانات والـRuntime والعرض. آخر ردي شات استغرقا 34760 و40596 مللي ثانية، وبعض ردود تحليل Agent نحو 104 ثوانٍ؛ سبب البطء الداخلي غير مثبت. قِس مسار الشات ومراجعة الملفات، وحجم السياق وعدد طلبات الموديل، قبل اختيار تحسين محدود.

**معيار القبول:** قياسات قبل وبعد لنفس الطلبات، مع تقليل الانتظار المثبت دون حذف سياق لازم أو اختبارات دليل أو خطوات صلاحيات. لا انتظار غير محدود ولا إعادة إرسال صامتة، ويظهر تقدم مناسب. تُسجّل أي حدود أداء باقية صراحةً في تسليم النسخة.

### 5 إعادة التحقق بعد آخر تعديل

شغّل اختبارات الإصلاحات المركزة ثم اختبارات Backend وFrontend، والـtypecheck للطرفين، وفحوص PostgreSQL المنفصلة، واختبار الإدارة والعزل والجلسات الحقيقي. اعرض المتخطاة وما إذا شُغلت منفصلة. لا تعتبر غياب أخطاء الملفات المعدلة نجاحًا للـtypecheck كله.

**معيار القبول:** صفر فشل في النطاق المطلوب، تفسير كل skip، عدم تغيير بيانات أو صلاحيات المستخدم الحقيقي أثناء fixtures، وعدم كسر المسارات العاملة. إذا احتاج الإصلاح تحديث الخدمة، أعد التحقق على عملية الخدمة التي تحمل آخر source فعلًا.

### 6 جولة القبول الحية النهائية

في النسخة الحالية نفّذ الشات، استمرار السياق، مراجعة متعددة الملفات بتقرير كامل، الإيقاف والاستكمال، المستكشف والبحث، التعديل المشروط وread-back، Reload وحفظ التاريخ، ولوحة الإدارة. تحقق من منع مستخدم قراءة شات مستخدم آخر، ومنع تجاوز الفولدر، وإبطال جلسة الحساب الموقوف. فحوص العزل على fixtures الحقيقية تكمل الواجهة؛ لا تدّع جلستي متصفح مستقلتين إن لم تُنفّذا.

**معيار القبول:** كل مسار أساسي يحقق النتيجة المطلوبة فعلًا، بإيصالات وسجل نهائي ثابتين، دون فقد أو تكرار أو bypass. عدم اكتمال التقرير أو الكتابة يبقي القرار NOT_READY.

### 7 حفظ النسخة المرشحة وإصدار قرار القفل

احفظ snapshot جديدًا بعد الإصلاحات الأخيرة وبصمات ملفاته، نتائج الاختبارات، تقرير القبول، القيود الباقية، وخطوات تشغيل واستعادة مفهومة. افحص build في مكان معزول حتى لا يستبدل ملفات dev الحية، إن كان build ضمن النسخة المرشحة. راجع الملفات المعدّة لـGitHub لإبعاد env والمفاتيح وحالة Runtime وبيانات المستخدم والسجلات الخام.

**معيار القبول الأخير:** أعلن **READY_FOR_LOCAL_MVP** فقط بعد نجاح بوابات 1 إلى 6 على نفس النسخة وتسليم أدلتها. يظل وصف النسخة محليًا؛ نجاح build أو health لا يثبت النشر أو اتصال جهاز آخر. رفع GitHub والنشر لا يحدثان لمجرد اكتمال هذه الوثيقة.

## بعد قفل النسخة المحلية

1. تجهيز مستودع GitHub وملفات البيئة والتعليمات، مع تحديد النسخة المرشحة ومراجعة الأسرار قبل النشر.
2. تجهيز backend على السيرفر مع HTTPS وقاعدة البيانات والإعدادات الصحيحة وخطة backup واستعادة؛ فحص migration المقترحة والهدف قبل تطبيقها.
3. توفير Runtime installer موثوق وربط جهازين فعليًا؛ اختبار اتصال كل مستخدم بجهازه وفولدره وعزلهما، والانقطاع والاستكمال والإبطال. فتح الفولدر المحلي يظل عبر Runtime على جهاز المستخدم، ويتصل بbackend السيرفر؛ استضافة الموقع وحدها لا تمنح الوصول لملفات الجهاز.
4. إثبات النشر الحي والـRuntime عبر عنوان السيرفر، ثم التعامل مع الجاهزية للإنتاج كقرار مستقل.

هذه الخطوات اللاحقة غير منفذة في هذا التسليم. أحدث مرجع للقبول هو `backend/.runtime-state/mvp-acceptance-report.json`، وتُحدّث النتيجة بعد الاختبار التالي بدل استنتاجها من نتائج قديمة.
